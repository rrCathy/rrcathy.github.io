写给两类人。一类是学过群论、见过凯莱图插图但没自己画过的；一类是写前端、想搞清楚一张「数学插图」背后要多少工程量。中间那节是能跑的代码，最后那节是引擎的实现取舍。

一、凯莱图是什么

一句话能说完。

给定群 GGG 和它的一组生成元 SSS，凯莱图的节点就是 GGG 的每个元素；对每个 x∈Gx\in Gx∈G 和每个 s∈Ss\in Ss∈S，从 xxx 拉一条边到 xsxsxs。

节点是元素，边是「乘一个生成元」。沿着边走，等于不断做乘法。

先看个具体的。S3S_3S3​ 是三个元素的置换群，6 个元素：恒等 eee、三个对换 (12),(13),(23)(12),(13),(23)(12),(13),(23)、两个 3-循环 (123),(132)(123),(132)(123),(132)。

选生成元 a=(12)a=(12)a=(12)、b=(23)b=(23)b=(23)，从每个元素出发右乘它们，看走到哪。下面这张表是引擎算的，不是我写的。

(12)(12)(12)eee(123)(123)(123)
(123)(123)(123)(13)(13)(13)(132)(132)(132)

6 个元素摆一圈，两种生成元各用一种颜色连边，就得到一张图。

6 个节点、6 条边，每个节点都连两条边，围成一个环。这就是 S3S_3S3​ 在这组生成元下的凯莱图。悬停任意节点能读到它是哪个元素，拖动还能挪位置。

二、手绘一张凯莱图

刚才那张是引擎画的。回到纸上，同一张图怎么用手画出来。

拿 A4A_4A4​ 当例子，12 个元素，比 S3S_3S3​ 大一圈，手绘的每一步都看得清楚。A4A_4A4​ 是正四面体的旋转群：拿一个正四面体，所有能让它转完还和原来重合的转法，一共 12 种。没读过第一篇也没关系，这里只要记住「12 个元素」就够了。

选它还有个原因：这一节末尾会看到，同一个 A4A_4A4​ 换一组生成元，节点一个不动、图却完全变样。凯莱图不是群的属性，是「群加一组生成元」这个配对的属性——这句话是全篇的引子，先画一遍就明白它从哪来。

取生成元

a=(12)(34)(2 阶),b=(234)(3 阶).a=(12)(34)\qquad(\text{2 阶}),\qquad b=(234)\qquad(\text{3 阶}).a=(12)(34)(2 阶),b=(234)(3 阶).

手绘的流程是这样的。

第一步，列出所有元素。 12 个，写在纸上。

e   (234)   (243)   (12)(34)   (123)   (124)
(132)   (134)   (13)(24)   (142)   (143)   (14)(23)

第二步，给每个元素算两条「出口」。 从 xxx 出发，x⋅ax\cdot ax⋅a 和 x⋅bx\cdot bx⋅b 分别去哪。这里有个小技巧：bbb 是 3 阶的，所以 x⋅bx\cdot bx⋅b 和 x⋅b2x\cdot b^2x⋅b2 是两条不同的 bbb-边，都要记。aaa 是 2 阶，x⋅ax\cdot ax⋅a 和 a⋅xa\cdot xa⋅x 是同一个，一条 aaa-边就够。

这一步只能一个个乘，没有捷径。乘法规则是置换的复合，A4A_4A4​ 比 S3S_3S3​ 多了几对双对换，手算要留神。

第三步，按「bbb-边围成三角形」来摆。 这是手绘 A4A_4A4​ 时最省事的一招。看 bbb 生成的循环子群

⟨b⟩={e, b, b2}={e, (234), (243)},\langle b\rangle=\{e,\ b,\ b^2\}=\{e,\ (234),\ (243)\},⟨b⟩={e, b, b2}={e, (234), (243)},

这三个元素两两之间都是 bbb-边，形成一个三角形。把它整个复制 4 份，A4A_4A4​ 就被剖成了 4 个三角形。

这 4 个三角形就是 ⟨b⟩\langle b\rangle⟨b⟩ 的 4 个右陪集：每个三角形内部由 bbb-边连成闭合的环，三角形之间用 aaa-边相连。

{ e, (234), (243) }        { (12)(34), (124), (123) }
{ (132), (134), (13)(24) } { (142), (14)(23), (143) }

第四步，用 aaa-边把 4 个三角形缝起来。 每个元素伸出一条 aaa-边，指向另一个三角形里的某个元素。aaa 是 2 阶的，所以这条边是双向的，两个三角形互相连着。

画完是这样的：4 个三角形，两两之间有一条边。

这张图有 12 个节点、18 条边，每个节点连 3 条边（一条 aaa-边加两条 bbb-边）。数学上叫 3-正则。数一遍：4 个三角形，每个内部 3 条 bbb-边，共 12 条；三角形之间 6 条 aaa-边。12+6=1812+6=1812+6=18。

引擎给 A4A_4A4​ 的默认 2D 布局是截角四面体的等轴投影，源码里叫 projection3D。4 个三角形确实画出来了，青色 bbb-边在每簇内部连成三边。但投影之后，立体上分开的顶点有两两重叠到一处，12 个节点挤成三簇，三角形看着反而糊。

换成 3D 布局，三角形结构就清爽了。引擎把每个陪集铺成一个平面三角面。

立体版一眼能看出形状：12 个顶点就是一个截角四面体，把正四面体的四个尖角削平得到的那个立体。

换成另一组生成元 (234),(134)(234),(134)(234),(134) 试试。元素还是那 12 个，群还是 A4A_4A4​，节点位置甚至没动，但图变了：现在每个元素连 4 条边，总边数 24，再也不是截角四面体。

开头说的那句在这里落地了：换生成元，节点数不变，边数和形状全变。 记住这组对比，第三节的代码和第四节的引擎，最后都要回到它身上。

三、用代码生成一张

手绘的流程，一步一步都能翻译成代码。

先说最小可用的版本。不用任何库，会写循环就行。核心只有一句话：对每个元素、每个生成元，算出乘完是谁，连一条边。

// group 需要提供：elements（元素列表）、multiply(a, b)（群乘法）
function buildCayleyEdges(group, generators) {
  const edges = []
  for (const x of group.elements) {
    for (const s of generators) {
      const y = group.multiply(x, s)   // 右乘：x → x·s
      edges.push({ from: x.id, to: y.id, gen: s.id })
    }
  }
  return edges
}

就这些。buildCayleyEdges 返回一个边表，每条边记着「从哪个元素、乘哪个生成元、到哪个元素」。这就是凯莱图的全部结构。

还是拿第二章那个 A4A_4A4​ 试，生成元 a=(12)(34)a=(12)(34)a=(12)(34)、b=(234)b=(234)b=(234)。按引擎的元素顺序跑，前几行是这样：

e       --a--> (12)(34)   --b--> (234)
(234)   --a--> (132)      --b--> (243)
(243)   --a--> (142)      --b--> e
...

12 个元素乘 2 个生成元，24 条记录。手绘时第二步算的那张「出口表」，就是这段代码的输出。

但 24 条记录不对应 24 条边。(12)(34)(12)(34)(12)(34) 是 2 阶的，x⋅ax\cdot ax⋅a 和 xa⋅axa\cdot axa⋅a 是同一对端点的两个方向，12 条记录两两配对，实际只有 6 条 aaa-边。(234)(234)(234) 是 3 阶的，x→xb→xb2→xx\to xb\to xb^2\to xx→xb→xb2→x 是个三元环，12 条记录各是一段不同的有向边，一条都不能合并。

6+12=186+12=186+12=18，这才是 A4A_4A4​ 在这组生成元下的真实边数。手绘时你画一条线就完了，代码里得先判断：这条边要不要合并？

想清楚要画有向还是无向，是第一个岔路口。

生成元自逆（s2=es^2=es2=e）时，边是双向的，画一条不画箭头。生成元不自逆（比如 A4A_4A4​ 里的 (234)(234)(234)）时，x→xsx\to xsx→xs 和 xs→xssxs\to xssxs→xss 是两条不同的边，bbb-边构成环，环有方向。

上面那段代码只解决了「算出边」。要真正显示出来，还得解决三件事：

  1. 元素怎么摆。 给每个元素算一个二维坐标。
  2. 边怎么画。 SVG 里就是 <line> 或 <path>。
  3. 交互。 拖动、悬停、点击。

最小版本可以偷懒，把元素按列表顺序直接摆成一个圆。

function CayleyFigure({ group, generators }) {
  const raw = buildCayleyEdges(group, generators)

  // 上面那步会给每条自逆边正反各记一次，这里按端点去重
  const seen = new Set()
  const edges = raw.filter(e => {
    const k = [e.from, e.to].sort().join('|') + '|' + e.gen
    if (seen.has(k)) return false
    seen.add(k)
    return true
  })

  const n = group.elements.length
  const R = 130
  // 均匀排在圆周上，从正上方开始
  const pos = new Map(group.elements.map((el, i) => {
    const t = (2 * Math.PI * i) / n - Math.PI / 2
    return [el.id, { x: 200 + R * Math.cos(t), y: 200 + R * Math.sin(t) }]
  }))

  return (
    <svg viewBox="0 0 400 400">
      {edges.map((e, i) => {
        const p = pos.get(e.from), q = pos.get(e.to)
        return <line key={i} x1={p.x} y1={p.y} x2={q.x} y2={q.y}
                     stroke={e.gen === generators[0].id ? '#e5484d' : '#0d9488'} />
      })}
      {[...pos.values()].map((p, i) => (
        <circle key={i} cx={p.x} cy={p.y} r={22} fill="#fff" stroke="#333" />
      ))}
    </svg>
  )
}

三十来行，能出一张图。用 S3S_3S3​ 跑一下（生成元 (12)(12)(12)、(23)(23)(23)），六个点排一圈，正好是第一节那张正六边形——它的默认元素顺序让两条边都落在相邻位置上，纯属运气。

换成 A4A_4A4​ 就没这个运气了。同一个函数，同一份边表，六个点变成十二个点排在更大的圆上，手绘时那 4 个三角形全散了，bbb-边从圆上斜穿过去，互相打结。

问题不在代码，在「按顺序摆圆」这个假设。 它对 S3S_3S3​ 成立是巧合，对 A4A_4A4​ 不成立，再往上的群只会更糟。

原因在第一节就埋下了：凯莱图的形状不是数学给死的，是布局算法选的。 手绘时你靠直觉把 bbb-边围成三角形，代码里得把这种直觉写成规则。按「bbb-边优先」摆，4 个三角形自然聚拢；按列表顺序摆，它们必然散开。同一份边表，两种布局，可读性差很远。

这个分歧，就是从一个玩具代码长成一个引擎的起点。

四、引擎里发生了什么

到这一步，脚本能画一张图了。但真要让它在网页上对着各种群都画得好看、还能交互，就得回答上面那些岔路口。

后面几节拆的是 GroupViz 的引擎，github.com/rrCathy/GroupViz。先把利益关系交代清楚：它是我自己写的，为教学做群论可视化，文章里的活图都出自它。所以这不算分析别人的代码，算把自己的取舍摊开——哪些是算的，哪些是存表，哪些我自己也不满意。

4.1 边：局部计算，全局查表

引擎的第一步和上面那段代码一样：对每个元素、每个作用元素，算乘法、连边。

// src/core/algebra/cayleyEdges.ts
for (let i = 0; i < group.elements.length; i++) {
  const fromEl = group.elements[i]
  for (const action of enabledActions) {
    const actionEl = actionElementMap.get(action.elementId)
    if (!actionEl) continue
    let toEl = multiplyType === 'right'
      ? group.multiply(fromEl, actionEl)
      : group.multiply(actionEl, fromEl)
    // ...查索引、判断自环、推入 allEdges
  }
}

有三处细节值得说。

一、multiplyType。 右乘算 x⋅sx\cdot sx⋅s，左乘算 s⋅xs\cdot xs⋅x。这不是可有可无的选项。x⋅sx\cdot sx⋅s 和 s⋅xs\cdot xs⋅x 一般不等，两种走法给出两张不同的图。对非交换群，左右乘的凯莱图甚至可能不同构。

二、isSelfLoop。 s=es=es=e 时 x⋅e=xx\cdot e=xx⋅e=x，边是自环。自环要单独画成一个小圈，不能用普通边。

三、末尾的去重。

const key = `${Math.min(fromIdx, toIdx)}|${Math.max(fromIdx, toIdx)}|${actionElementId}`

按「小索引|大索引|作用元素」拼 key。x→xsx\to xsx→xs 和 xs→xxs\to xxs→x 因为端点相同、作用元素相同，会拼出同一个 key，只留一条。这一步把有向边表压成了无向边表。

还有一道防线：群阶超过 60 时，边数上限设为 max⁡(120,3n)\max(120, 3n)max(120,3n)。S5S_5S5​ 有 120 个元素，不设限边数会爆炸，页面直接卡死。这是工程对数学的妥协。大群不做全展开，只画一部分。

4.2 布局：一条逐级降格的决策链

边算完了，怎么摆是第二个大问题。这是引擎里最长的一段逻辑。

getDefaultLayout3D 是个瀑布式的判断，从上往下，命中就返回。整条链大致是：

商群 → 半直积 → C₂³ → C₂⁴ → 直积 → 二面体 → 循环群 → 阿贝尔 → 特定群（S₃、Q₈、Q₁₆、A₄、A₅、S₄ 各有名分）→ 其余 Sₙ、Aₙ → 兜底

每一级对应一种布局：二面体拿双环，A4A_4A4​ 拿截角四面体，S3S_3S3​ 拿六边形，名字都写在源码里。

判断顺序不是随意的。直积要排在阿贝尔前面，否则 C2×C2C_2\times C_2C2​×C2​ 会被当成普通阿贝尔群画成圆而不是四面体。C23C_2^3C23​ 要排在直积前面，否则立方体会被网格布局顶掉。

这条链暴露了一件事：形状是按「群的性质」分配的，不是按群阶。 同样是 12 阶，A4A_4A4​ 拿截角四面体，C12C_{12}C12​ 拿圆，D6D_6D6​ 拿双环。群阶只决定节点数量，不决定形状。

注意这条链只认「群是谁」，不认「生成元是谁」。A4A_4A4​ 连上去就是截角四面体，不管你传的是哪两个生成元。这是引擎的设计前提，也是它最大的软肋——下一小节就是这条前提翻车的地方。

4.3 多面体顶点：算一次，存下来

A4A_4A4​ 的 12 个元素落在截角四面体的 12 个顶点上。这些坐标引擎是当场算的吗？

不是。

// src/core/algebra/layouts3D/archimedeanLayouts3D.ts（节选）
if (n === 12) {
  const faceIds: string[][] = [
    /* 4 组 × 3 个元素 id，此处省略 */
  ]
  const verts = truncatedTetrahedron(radius)
  // 把元素 id 逐个映射到顶点
}

faceIds 是 4 组、每组 3 个元素 id。这 4 组是 A4A_4A4​ 里 4 个 C3C_3C3​ 子群的陪集，也就是手绘时那 4 个三角形。每一组映射到截角四面体的一个三角面。

群论的对应关系被硬编码成了一张表。 引擎不每次去求解「哪个元素该在哪个顶点」，而是事先算好、写成常量。运行时只做查表。

这是性能选择，也是正确性选择。多面体顶点的数学生成（把元素按共轭类或陪集分配）容易出现边界情况，硬编码一张表反而更稳。代价是这张表只认「A4A_4A4​ 这 12 个 id」，换个群就整表作废。

4.4 换个生成元，形状就崩了

上一小节说硬编码「更稳」。这个结论只在一个前提下成立，而这个前提经常不成立。

A4A_4A4​ 用 (12)(34),(234)(12)(34),(234)(12)(34),(234) 时，12 个元素正好占满截角四面体的 12 个顶点，完美。换成 (234),(134)(234),(134)(234),(134) 呢？第二节末尾那张立体图就是。

顶点还是那 12 个，但边变了：现在每个元素连 4 条边，而截角四面体是 3-正则的，每个顶点只有 3 条边。图的度数和立体的顶点度数对不上了。

这时候「崩」崩的不是画面——图还能看，缩放两下什么都清楚——崩的是名实：硬编码的坐标表只能用一半，元素的位置还有效（位置跟元素走，不跟边走），形状已经名不副实。你看到的是「12 个球摆成截角四面体，但边的连接方式不是截角四面体」。

引擎的处理是：位置照旧查表，边照新生成元算，两者不强求一致。结果是图还能看，但它不再「长得像」截角四面体了。

要真正做到「换生成元，形状跟着变」，得让形状由边的结构推出来，而不是由元素的性质推出来。这就是另一条路，也是形状选择这个主题的核心，它值得单独一篇，这篇先到这儿。

4.5 作用元素不限于生成元

顺着这个局限，还有一处引擎和教科书不一样的地方。

教科书定义凯莱图时，SSS 必须是生成元集。引擎允许 SSS 是任意群元素集，只要图还连通、还叫凯莱图。

以 A4A_4A4​ 为例，取 S={(12)(34),(234),(134)}S=\{(12)(34),(234),(134)\}S={(12)(34),(234),(134)}，三个元素，其中前两个就能生成整个 A4A_4A4​，第三个是多余的。引擎照样画，只是第三个元素带来的边和已有的重叠或重复。

这个宽松是有用的。教学时想「只高亮某几个元素的边」看结构，不用先论证它们生成不生成整个群。

严格说，SSS 不含群的生成元时，图可能不连通，那就不是标准凯莱图，而是广义凯莱图。引擎的名字里没区分，但代码里 actions 的类型注释写着「广义凯莱图：任意群元素，不限于生成元」。

五、为什么 S₃ 是六边形

回到第一节留的那个问题。

答案不在算法里，在项目的历史里。S3S_3S3​ 的凯莱图是整个项目最早画出来的图之一，比引擎早得多。当时没有算法可讲，就是拿着 6 个元素试顺序：怎么排，边才不交叉、看着舒服？试出来的答案是一个环。圆环，好看，定下来。

引擎是后来才动手的，路径也和直觉相反：不是先写算法再画图，而是各种群的凯莱图形状在一次次迭代里逐个敲定、编码下来，敲得差不多了，再把这些既定形状收编进引擎。S3S_3S3​ 这张环序表就是那时候原样抄进去的。

// src/core/algebra/ringOrder.ts
export const S3_PERM_IDS = ['1,2,3', '2,1,3', '2,3,1', '3,2,1', '3,1,2', '1,3,2']

引擎认出 S3S_3S3​，就按这个顺序摆圆。摆出来是什么样？

e --(12)--> (12) --(23)--> (123) --(12)--> (13) --(23)--> (132) --(12)--> (23) --(23)--> e

相邻两个元素之间差一个 (12)(12)(12) 或 (23)(23)(23)，两条边交替，绕圆一圈用完所有元素。于是正六边形，边上零交叉。

这个顺序是挑出来的，不是推出来的。 挑法很朴素：边一旦交叉，图就没法看，环状最干净。4.3 那张多面体顶点表是同一个模式，先由人眼敲定，再固化成表，运行时只管查。

这个选择有它的代价。第一节那句括注说的就是这个意思，长得像正六边形，不是数学逼出来的。S3S_3S3​ 换一组生成元 (12),(123)(12),(123)(12),(123)，这张表就失效了：(12)(12)(12) 和 (123)(123)(123) 的边不再沿圆相邻，图从 6 条边涨到 9 条，六边形没了。

节点还是按老顺序摆在圆周上，但边不再沿着圆周走，而是横穿过去绞在一起。这张图的两个青色三角形对应 ⟨(123)⟩\langle(123)\rangle⟨(123)⟩ 的两个陪集，三个红色 (12)(12)(12)-边把两层连起来，结构上是个三棱柱。

但引擎只把节点摆圆，没按三棱柱铺，所以画出来是这样一张交叉的图。

数学上这两张都是 S3S_3S3​ 的凯莱图，平等。可读性上差很多。引擎保了六边形那张，代价是只对这一组生成元好看。

六、回头看这四步

用手画一张 A4A_4A4​ 的凯莱图，靠的是「把 bbb-边围成三角形」这个直觉。

用代码画，直觉要变成规则：算边表、选布局、画 SVG。最小版本三十来行能跑，但换个群、换组生成元就露怯。

引擎要面对的，是「所有群、所有生成元、还要好看、还要能交互」。它给出的答案里，有能推广的部分（边计算、决策链、投影），也有硬编码的部分（多面体坐标表、S3S_3S3​ 环序）。硬编码不是偷懒，是权衡。有的表是算不动才存的，比如多面体顶点；有的表是早就有、没必要重算的，比如 S3S_3S3​ 环序。

这张表好不好，取决于它覆盖多少情况。S3S_3S3​ 的六边形覆盖了默认生成元，换个生成元就失效。A4A_4A4​ 的截角四面体覆盖了一组漂亮的生成元，换一组就名不副实。引擎的好看，很多时候建立在「读者不换生成元」这个默认前提上。

这个前提为什么难破？

因为引擎到现在为止，一直在从元素的性质推形状。A4A_4A4​ 之所以拿到截角四面体，是因为「A4A_4A4​ 是正四面体的旋转群，12 个元素对应 12 个顶点」，这个对应关系是群论给的、写死在表里的。它跟边无关。

但只要换一组生成元，边就变了，图的连通结构也变了。这时候真正决定「图长成什么样」的，是边，不是元素。而引擎手里那套按群性质分配形状的机制，根本没有把边作为输入。

所以要换思路：让布局算法读边表、认结构，从「谁和谁相连」反推出该怎么摆。这件事比查表难得多——它要把「这个图是截角四面体的骨架」这种判断从人眼直觉变成算法，而图的同构判定本身就没有便宜的解。

具体怎么做、能不能做得动、哪些群能做哪些做不了，是下一篇的事。
